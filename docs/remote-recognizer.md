# Удалённое распознавание Windows

Fono записывает звук на Windows и отправляет выбранному Fono Server. Захват, hotkey, Лира, обработка текста и внешняя вставка остаются на Desktop. Server заменяет источник STT. Схемы и подключение других приложений — в [API](api.md).

## Подключение

В настройках аудио выберите Fono Server: имя подключения, способ доступа, API-токен, проверка сервера, установленная модель и политика резерва. Сохраните токен и настройки. Проверка черновика сама не сохраняет подключение, не отправляет аудио и не переключает движок.

Прямой межмашинный доступ требует HTTPS с доверенным сертификатом. Публичный CA частного сервера можно задать для подключения; отключать TLS-проверку нельзя. HTTP допускается только на loopback, включая конец защищённого туннеля.

### Управляемый SSH

Выберите SSH, задайте хост, порт, пользователя и существующий private-key файл либо разблокированный SSH-agent Windows. Порт API на сервере обычно 17832. Требуется OpenSSH Client Windows. Fono создаёт собственный скрытый канал к remote loopback; отдельная команда и ручной запуск туннеля не нужны.

Получите публичный host key, сравните SHA256-отпечаток с доверенным значением администратора и подтвердите доверие. **Отпечаток не является API-токеном.** Токен выдаётся отдельно в панели. Смена ключа не принимается молча; изменение SSH-назначения сбрасывает проверку черновика.

Fono использует строгую проверку закреплённого ключа и public-key authentication. Private key не копируется в настройки, SSH-пароль не сохраняется; для защищённого ключа нужен подготовленный агент. Приложение не открывает remote shell и не меняет OpenSSH config. Обход конкретной ошибки ssh-keyscan получает только кандидат ключа в изолированном файле без пользовательских credentials; ему всё равно нужно явно довериться.

Управляемые процессы и сокеты закрываются при смене источника и завершении приложения. Сторонний ручной туннель приложением не присваивается.

## Совместимость и переключение

Discovery сверяет API version, возможности и выбранную модель до передачи аудио. Patch-версии клиента и сервера не обязаны совпадать. Недоступная модель не становится готовой из-за обновления списка.

Переключение требует простоя: диктовка, pending-результат, фоновые операции и API-задания удерживают admission. Новый backend готовится до сохранения, ошибка не выдаёт неподтверждённое подключение за выбранное. Локальные модель, ускорение и residency сохраняются для возврата.

Remote startup не загружает локальные веса и не запускает локальное восстановление GPU-модели. Безопасный успешный переход завершает прежний idle worker. Это не обещание нулевого расхода всей VRAM: Лира и другие приложения имеют независимые ресурсы. Реальный расход GPU и возврат источника проверяются отдельным native-сценарием.

## Ошибки, повтор и резерв

Preflight идёт параллельно записи, привязан к её operation ID и не задерживает захват. Поздний ответ не меняет следующую сессию. Основное аудио отправляется после Stop в PCM, без клиентского Opus-сжатия.

При отказе PCM остаётся у соответствующей операции. По выбранной политике доступны явный повтор, установленная локальная CPU-модель или решение пользователя. Скрытой загрузки модели и автоматического replay после обрыва нет. Cancel запрещает позднюю публикацию и вставку, но ресурсы освобождаются после фактической фоновой работы.

История отражает реальный remote backend, модель и измеренные длительности сессии, fallback отмечается отдельно. Диагностический экспорт не содержит адреса подключения, SSH-реквизитов, токенов, аудио и текстов.

## Сценарии и границы

Обычная диктовка, пробная диктовка обработки, транскрибация голосовых команд и голосовых инструкций редактирования используют выбранный источник. Файловый экран создаёт серверное batch-задание. Проверка микрофона и Лира остаются локальными.

Desktop API пока требует Local: forwarding не реализован. Предраспознавание remote-сегментов, Opus-сжатие клиента и сторонний OpenAI backend не включены. Наличие соответствующего серверного маршрута не означает эти функции клиента.

Контрактные/сквозные проверки покрывают listener, авторизацию, busy, таймаут, обрыв, повтор, отмену и реальный CPU-образец. Они не заменяют приёмку микрофона, hotkey, внешних приложений, всех резервных политик, отмены/позднего ответа и восстановления подключения после перезапуска. Порядок — в [testing](testing.md).
